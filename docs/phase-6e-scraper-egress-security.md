# Phase 6E scraper egress and credential boundary

Scope: stacked on Batch 3 commit `e0f6ee3a20f2148c335c69cd3919cda9bf601c0b`. This change does not authorize a deployment or enable website chat or file uploads.

## Reproduction and patched behavior

| Finding | Previous path | New boundary | Controlled evidence |
| --- | --- | --- | --- |
| B3-S1 (high) | Authenticated `/api/scrape/start` or `/refresh` accepted an internal URL; the worker's direct-HTML fallback followed redirects with native `fetch` to that destination. | Routes reject unsafe URL shapes/DNS answers before inserting jobs. The worker rechecks old or forged jobs. Each direct-HTML hop resolves all answers, rejects any non-public answer, and uses the selected address in the transport's `lookup` callback (no independent hostname resolution); only GET with fixed non-secret headers is sent. Redirects are manual, revalidated and bounded at five hops. | `test/scrapeDestinationPolicy.test.js`, `test/security.test.js`, `test/firecrawlCredentialIsolation.test.js`. These are controlled no-network fixtures, not a deployed egress test. |
| B3-S2 (high, conditional) | An absolute Firecrawl `next` URL was fetched with the configured Authorization or x-api-key header, even off-origin. | The API origin is parsed from trusted configuration. Pagination and each manual redirect must match its exact scheme/host/effective port; userinfo and malformed URLs fail closed. POST redirects are refused. Requests cannot follow an off-origin `next` with credentials. | `test/firecrawlCredentialIsolation.test.js` asserts a dummy token/key never reaches a second origin, including lookalikes, downgrades, ports and redirects. |

The website policy accepts HTTP/HTTPS on default ports 80/443 only, without URL userinfo; it rejects loopback, private, link-local, multicast, reserved and metadata IPs, including IPv4-mapped IPv6 and WHATWG-normalized alternate numeric representations. Mixed DNS answer sets fail closed. DNS resolution happens again at each outbound direct connection and on redirects. A 30-second per-hop request deadline and 2 MiB direct response cap apply. Firecrawl response bodies are capped at 8 MiB with a request deadline; pagination is capped at 50 pages. Provider errors and URLs are not copied into scrape job error strings or scraper logs.

## Residual trust and deployment conditions

- Firecrawl's configured self-hosted/official API origin is an **operator-trusted** endpoint. The code confines credentials to that origin, but does not pin its DNS or govern how the remote Firecrawl service fetches an untrusted website. A remote crawler must independently enforce equivalent destination/redirect rules and egress restrictions. DNS responses may differ between API preflight and remote crawling. HTTP self-hosted configuration is still supported for legacy compatibility; use HTTPS with certificate verification and a trusted origin in deployment.
- The application policy protects this direct-HTML client, not every outbound request elsewhere in the backend. No deployed network firewall or reverse-proxy behavior was verified. Restrict scraper egress at the network layer: deny loopback, RFC1918/ULA, link-local and cloud metadata endpoints, control-plane addresses and service networks; allow only intended public HTTP(S) and the configured Firecrawl API. Apply the restrictions to both API and any separate scraper/Firecrawl worker, accounting for DNS rebinding and IPv6. Verify actual container routes, DNS behavior and proxy configuration before enabling untrusted scraping.
- The route's DNS check is an early rejection and can differ from a later answer. The worker checks again; the direct transport pins the vetted answer for each hop. Network egress filtering remains necessary defense in depth, including against transport, resolver or upstream-provider behavior that tests cannot prove in a container deployment.
- The response-size cap is not a total job-memory budget: up to 50 provider pagination responses and extracted pages may accumulate, and multiple authenticated jobs can run. Review memory and concurrency with actual container limits. The existing 150 MiB authorized-upload concurrency, ingress, and cross-container file-handoff blockers remain. Staging proxy behavior, PostgreSQL TLS verification and real HTTPS authentication/session testing remain separate preflight items. No migration or deployment is authorized.

Known compatibility restriction: a Firecrawl deployment that redirects POST API calls, moves pagination to another origin, uses a non-HTTP scheme, or requires a provider response larger than the configured cap now fails closed. Configure the service at its final trusted origin rather than weakening the credential boundary.
