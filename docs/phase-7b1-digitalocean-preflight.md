# Phase 7B.1 DigitalOcean private preflight (review only)

Base: `520cace9bd18cea0cda76cba17207d59939c6f7b`. Nothing in this proposal has been deployed, provisioned, purchased or migrated. The Render blueprint remains blocked; this is a separate proposed topology, not an authorization to apply `digitalocean.staging.yaml`.

## Provider evidence and intended topology

- DigitalOcean documents internal-only App Platform services with `internal_ports` and no `http_port` or ingress route: https://docs.digitalocean.com/products/app-platform/how-to/manage-internal-routing/ . The review-only spec uses a single LON (`lon`) internal service, manual deployment (`deploy_on_push: false`), no worker, jobs, database component, public ingress or automatic migration. A dedicated LON1 VPC and its actual association to the app and databases **must be checked through provider configuration and a live deployment record**; merely declaring `region: lon` does not create or prove a VPC.
- App Platform documents `${_self.COMMIT_HASH}` as the commit used for the service build: https://docs.digitalocean.com/products/app-platform/how-to/use-environment-variables/ . The spec binds it for build and runtime. The build command compares it with the actual checked-out `git rev-parse HEAD` and the separately approved SHA, then emits a local (ignored) attestation. Startup compares that attestation, the provider binding, the approved SHA and the configured branch before any database/queue imports. If Git metadata or the bindable value is unavailable at build/runtime, startup fails. This does not establish a cryptographically signed provenance chain: an operator with spec/environment write access could replace the binding. Independently inspect the DigitalOcean deployment record (repo, branch, exact commit and spec revision) before and after deployment; reject an unexpected commit or moving branch. No automatic push-triggered deployment is permitted.
- Managed PostgreSQL Standard provides downloadable CA and `verify-full`; pgvector and PostgreSQL 16 are supported: https://docs.digitalocean.com/products/databases/postgresql/how-to/connect/ and https://docs.digitalocean.com/products/vector-databases/postgresql/how-to/enable-pgvector/ . Provision a dedicated staging cluster/database and API role with read-only privileges. The API accepts only a pinned `*.db.ondigitalocean.com` DNS name matching `STAGING_DATABASE_HOST`, requires CA PEM and `rejectUnauthorized: true` with TLS servername equal to the connection hostname. URL SSL query options are forbidden because node-postgres can replace the explicit SSL object: https://node-postgres.com/features/ssl . CA chain and private endpoint SAN must be verified against actual connection details later. Migration credentials must remain separate and are never injected into this service.
- Managed Valkey requires TLS and documents password authentication with a private endpoint: https://docs.digitalocean.com/products/databases/valkey/how-to/connect/ . For this path only, `rediss://:password@pinned-host:port/` (no username) is accepted, as is a username **only when separately pinned** by `STAGING_REDIS_USERNAME`. A dedicated staging cluster and restricted trusted sources are required. `ioredis` relies on Node TLS verification; validate the real CA chain, hostname and AUTH at deployment time. The infrastructure-only service must not start any queue worker.
- Private VPC reachability is not service authentication. Same-VPC lateral access, internal DNS and compromised credentials remain risks. Restrict database and Valkey trusted sources to this particular staging app as far as provider supports; use a dedicated workspace/project and VPC separate from production; inspect effective network ACLs and deny a distinct test service. Verify no production hosts/credentials appear in the spec or runtime. This is not proven by local tests.

## Required configuration before any later deployment approval

Keep secret values in provider secret storage, not a Git spec, CI artifact or log. The proposed file omits them deliberately and cannot pass the build/runtime preflight as checked in. Owner must review the final non-secret deployed spec and secret references for drift. Provider probe Host behavior is undocumented and **unresolved**: do not loosen the exact Host gate; verify the actual probe and select a single exact approved value before deployment. Health/readiness are the only routes; private service access itself still needs a controlled monitoring source and network isolation.

No migrations or initialization writes occur in ordinary startup; `/readyz` only probes `SELECT 1` and Redis `PING`. A separate guarded migration would require a distinct owner approval, exact target identity, backup/recovery and execution record. `STAGING_REHEARSAL_MODE=infra-only` refuses migration commands. Website agents, uploads, scraper admission/workers, provider calls and public authentication remain disabled. Use synthetic data only.

## Cost, resource caps and shutdown

Planning estimate only, **not spending approval**: App Platform Basic 512 MiB ~$5/month, PostgreSQL Standard starting ~$15/month, Valkey starting ~$15/month, base ~$35/month. Actual sizes, availability, storage, backups, transfer, monitoring, taxes and overages can increase it. Published prices: https://www.digitalocean.com/pricing/app-platform and https://www.digitalocean.com/pricing/managed-databases . The app is one 512 MiB instance; startup sets 8 maximum connections, 4 active requests and a 5-second request timeout. These are proposed rehearsal caps, not validated against deployed proxy behavior or memory headroom. Require owner-approved cost ceiling, alerts, shutdown date, deletion/rollback procedure and no-autoscale confirmation. Stop the app and revoke disposable credentials after the rehearsal; take an approved backup before any separately authorized schema write.

1. Owner explicitly approves exact code SHA, final provider app spec/deployment record, LON1 region, dedicated VPC/project, resource sizes, monthly/overage ceiling and administrator account.
2. Verify App Platform really has no public route; probe from external network, permitted monitor and unrelated same-region service. Record health probe Host and forwarded headers; check rate limits, timeouts, body caps and concurrency at actual ingress.

4. Verify dedicated Valkey 8 private endpoint, TLS hostname/CA, AUTH password and trusted sources; show no worker or queue consumer starts, and no production cluster is referenced.
5. Compare provider deployment record to approved SHA, source branch and reviewed spec. Demonstrate checked-out Git SHA and `${_self.COMMIT_HASH}` binding work in provider build/runtime, or stop. Confirm attestation survives build packaging and cannot be replaced by a manually supplied environment value alone.
6. Verify only health/readiness GET/HEAD, disabled feature flags, absence of provider credentials, synthetic data, monitoring/log redaction, rollback and shutdown evidence. Real HTTPS auth and agents/uploads/scraping remain out of scope.

Local tests validate configuration functions, inherited health-only route gate and negative source/TLS/Valkey cases, not provider ingress, VPC isolation, managed database certificates, Valkey AUTH or billing. No deployment may proceed based solely on CI.
