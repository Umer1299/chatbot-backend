## Security-repair approval gates

The checked-in template now contains `vpc.id: OWNER_VPC_ID_REQUIRED` and a matching `STAGING_APPROVED_VPC_ID` placeholder. It remains intentionally nondeployable. DigitalOcean documents `vpc.id` in the app spec and maps app region `lon` to VPC datacenter `lon1`: https://docs.digitalocean.com/products/app-platform/how-to/enable-vpc/ . Before any separately authorized deployment, the owner must approve an actual VPC UUID and exact code SHA, export the **effective** provider spec, and compare it to the deployment record. Then run the offline validation command below in a controlled environment (without printing the spec, which can contain secret references):

`STAGING_APPROVED_VPC_ID=<owner-approved-uuid> STAGING_APPROVED_COMMIT_SHA=<approved-sha> node scripts/verify-digitalocean-effective-spec.js <provider-exported-spec-path>`

This rejects missing/placeholder/mismatched VPC IDs, wrong commit, duplicate YAML keys, unknown or public components, automatic deployment and incomplete required configuration. It does not authenticate the file's origin or prove actual VPC membership. The owner must compare provider record, actual VPC membership and trusted-source settings independently; a manually supplied environment value alone is not proof.

For all infrastructure-only connections, including the blocked Render path, startup rejects `NODE_TLS_REJECT_UNAUTHORIZED=0` and other malformed values. SA-01 requires authenticated `rediss://`, exact host pinning and explicit `rejectUnauthorized: true` with the pinned hostname on API, queue and readiness clients. Plaintext `redis://` now fails before client construction. Render production behavior outside infrastructure-only mode is unchanged; Render infrastructure-only deployment remains blocked for separate provider compatibility reasons. Controlled local handshakes prove certificate-chain and hostname rejection; actual provider certificate, AUTH and private endpoint behavior still require later deployed verification. No custom certificate acceptance callback is installed.

The future app's **VPC egress private IP**, not merely membership in the VPC, must be authorized in PostgreSQL and Valkey trusted-source settings where supported. VPC access is distinct from database/Valkey credentials and CA/hostname-verified TLS. Verify denial from unrelated same-region services. No DigitalOcean networking has been changed by this phase.

## Provider evidence and intended topology

- DigitalOcean documents internal-only App Platform services with `internal_ports` and no `http_port` or ingress route: https://docs.digitalocean.com/products/app-platform/how-to/manage-internal-routing/ . The review-only spec uses a single LON (`lon`) internal service, manual deployment (`deploy_on_push: false`), no worker, jobs, database component, public ingress or automatic migration. A dedicated LON1 VPC and its actual association to the app and databases **must be checked through provider configuration and a live deployment record**; merely declaring `region: lon` does not create or prove a VPC.
- App Platform documents `${_self.COMMIT_HASH}` as the commit used for the service build: https://docs.digitalocean.com/products/app-platform/how-to/use-environment-variables/ . The spec binds it for build and runtime. The build command compares it with the actual checked-out `git rev-parse HEAD` and the separately approved SHA, then emits a local (ignored) attestation. Startup compares that attestation, the provider binding, the approved SHA and the configured branch before any database/queue imports. If Git metadata or the bindable value is unavailable at build/runtime, startup fails. This does not establish a cryptographically signed provenance chain: an operator with spec/environment write access could replace the binding. Independently inspect the DigitalOcean deployment record (repo, branch, exact commit and spec revision) before and after deployment; reject an unexpected commit or moving branch. No automatic push-triggered deployment is permitted.
- Managed PostgreSQL Standard provides downloadable CA and `verify-full`; pgvector and PostgreSQL 16 are supported: https://docs.digitalocean.com/products/databases/postgresql/how-to/connect/ and https://docs.digitalocean.com/products/vector-databases/postgresql/how-to/enable-pgvector/ . Provision a dedicated staging cluster/database and API role with read-only privileges. The API accepts only a pinned `*.db.ondigitalocean.com` DNS name matching `STAGING_DATABASE_HOST`, requires CA PEM and `rejectUnauthorized: true` with TLS servername equal to the connection hostname. URL SSL query options are forbidden because node-postgres can replace the explicit SSL object: https://node-postgres.com/features/ssl . CA chain and private endpoint SAN must be verified against actual connection details later. Migration credentials must remain separate and are never injected into this service.
- Managed Valkey requires TLS and documents password authentication with a private endpoint: https://docs.digitalocean.com/products/databases/valkey/how-to/connect/ . The DigitalOcean path accepts `rediss://:password@pinned-host:port/` (no username), or a username **only when separately pinned** by `STAGING_REDIS_USERNAME`. Render infrastructure-only mode also requires verified TLS and its preexisting username/password contract. A dedicated staging cluster and restricted trusted sources are required. `ioredis` relies on Node TLS verification; validate the real CA chain, hostname and AUTH at deployment time. The infrastructure-only service must not start any queue worker.
- Private VPC reachability is not service authentication. Same-VPC lateral access, internal DNS and compromised credentials remain risks. Restrict database and Valkey trusted sources to this particular staging app as far as provider supports; use a dedicated workspace/project and VPC separate from production; inspect effective network ACLs and deny a distinct test service. Verify no production hosts/credentials appear in the spec or runtime. This is not proven by local tests.

## Required configuration before any later deployment approval

Replace the commit and VPC placeholders only in a separately reviewed provider configuration, not in the committed source template (embedding the final SHA in its own commit would be circular). Supply `STAGING_ALLOWED_HOST` (exact private Host including port, learned from controlled probe), `STAGING_REDIS_HOST`, `STAGING_DATABASE_HOST`, `DATABASE_URL` and identical `STAGING_DATABASE_URL`, `STAGING_DATABASE_CA_PEM`, `REDIS_URL` and identical `STAGING_REDIS_URL`, and optionally `STAGING_REDIS_USERNAME`. Keep secrets in provider secret storage, not Git, CI artifacts or logs. The checked-in file omits them and cannot pass build/runtime preflight as-is. Compare the actual effective spec and provider record to approved source and VPC IDs. Provider probe Host behavior is undocumented and **unresolved**: do not loosen the exact Host gate; verify it before deployment. Health/readiness are the only routes; private service access still needs controlled monitoring and network isolation.

No migrations or initialization writes occur in ordinary startup; `/readyz` only probes `SELECT 1` and Redis `PING`. A separate guarded migration would require a distinct owner approval, exact target identity, backup/recovery and execution record. `STAGING_REHEARSAL_MODE=infra-only` refuses migration commands. Website agents, uploads, scraper admission/workers, provider calls and public authentication remain disabled. Use synthetic data only.
