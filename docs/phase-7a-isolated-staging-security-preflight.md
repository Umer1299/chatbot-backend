# Phase 7A: isolated infrastructure-only staging preflight

This is a **review-only proposal**, not deployment approval. No infrastructure has been created, no migration has run, and no application, customer data or provider key may be used in the rehearsal. The older `docs/staging-validation.md` describes a later, feature-enabled exercise and MUST NOT be followed for this phase. The frontend remains unchanged and cannot connect to this private, health-only API; browser authentication and website-agent compatibility remain unverified.

## Approved source and topology

The branch `security/phase-7a-isolated-staging-security-preflight` derives from reviewed Batch 4 `e638d1ebbb8e0b53262de1ef5b474acf4610bd7d`; the PR targets Batch 4. The future owner must review the **final Phase 7A commit**, set `STAGING_APPROVED_COMMIT_SHA` to that exact 40-character SHA, and explicitly select that SHA for a manual deployment. `autoDeployTrigger: off` is not sufficient by itself: build/start both compare the approved SHA to Render's `RENDER_GIT_COMMIT` and verify the branch. An absent, different, or unavailable Render SHA aborts. Never move this lock automatically or deploy a moving branch tip. Verify Render's displayed deployed SHA against approval evidence. Never sync the blueprint merely to inspect it.

The proposed `type: pserv` API has no public onrender.com address. This is a *new* service name, not an in-place conversion of the older public `chatflow-staging-api`. Render private-network membership must be restricted to the intended staging workspace; the private network is not equivalent to per-caller authentication. Only GET/HEAD `/healthz` and `/readyz` are served; every application route, including aliases and trailing slashes, is blocked before authentication, parsers and handlers. Even health calls with bodies or forwarding identity headers are rejected. No worker service is defined. PostgreSQL 16/pgvector and Key Value use no public IP allowlist. Confirm actual provider firewall, DNS, private connectivity, response status, origin separation, health probe forwarding headers, resource quotas and no unintended old public staging service **in a separately authorized rehearsal**. CI cannot prove provider networking. The service is not an HTTPS/browser authentication test.

`ACCOUNT_PROXY_MODE=direct` and no `TRUSTED_PROXY_CIDRS` mean Express ignores client-supplied forwarding identity. The infra gate additionally rejects `Forwarded`, `X-Forwarded-For` and `X-Real-IP`. If a future reverse proxy is introduced, do not use blanket `trust proxy`; approve its exact CIDRs, topology, stripping/replacement of forwarding headers and quota identity in a new phase. Keep private health/readiness accessible only to authorized monitoring within the staging network. `/readyz` makes read-only database and Redis checks; it must not leak secrets.

Connections and active requests are explicitly bounded by owner-supplied `STAGING_MAX_CONNECTIONS`, `STAGING_MAX_ACTIVE_REQUESTS`, `STAGING_REQUEST_TIMEOUT_MS`; absence or invalid values abort. Node also caps HTTP headers at 8 KiB. The health-only gate rejects request bodies before any parser, but a proxy/load balancer can buffer bytes before Node; set and verify provider-side body, concurrent connection and idle time limits before creating the service. Select numeric values based on actual container memory, connection pools, burst patterns and provider limits; this document intentionally does not invent a safe cap. Ordinary startup uses `SELECT 1` and Redis `PING`, never vector table/index setup, reminder jobs, scrape polling or upload cleanup. CI tests that branch; production startup behavior is unchanged.

## TLS and secrets

Provision a dedicated, nonproduction, read-only PostgreSQL API role and paste only its credential into the *two matching* protected `DATABASE_URL` and `STAGING_DATABASE_URL` values. The blueprint does not hand the database-owner URL to the API. `STAGING_DATABASE_CA_PEM` must contain the trusted server CA; URL host must be a DNS hostname matching the certificate. The staging pool, separate migration client and readiness client all reject missing/mismatched CA, URL TLS overrides, IP-hostnames and invalid certificates. No `rejectUnauthorized:false` is used for isolated staging. **Before provisioning**, verify Render's actual PostgreSQL private endpoint supports certificate-verified TLS and supplies a usable CA/SAN; if not, stop rather than disabling validation. Production's existing TLS behavior is not changed here and remains a separate security issue.

The API alone accesses the staging Redis credential, sourced from the new private Key Value service. There is no worker credential because no worker runs. Any later worker requires separate least-privilege Redis/PostgreSQL credentials, isolated service identity and file-handoff design. Authentication/session secrets, JWT signing, API/worker internal authentication, Firecrawl/AI/email SDK credentials are deliberately absent; none may be copied from production. `ACCOUNT_AUTH_ENABLED=false`, the website flag is false, uploads and scraping are disabled, and the absence of a provider key is mandatory. The API gate and scraper enqueue/execution/outbound boundaries reject forged requests/jobs. Keep secret values out of GitHub, logs and artifacts. Use provider-managed secret storage and rotate on suspected disclosure.

## Migrations: a distinct future approval

The blueprint has no predeploy migration command. Its build/start scripts contain no migration invocation; the infra-only startup skips runtime DDL. The existing `npm run staging:migrate` command remains for a **later separately approved manual procedure**; it is not an authorized step now. Obtain written owner approval naming the exact code SHA, migration set `001`–`013`, database name and endpoint, account/role, backup ID, expiry and operator. Verify isolated database identity, PostgreSQL major version, pgvector availability, no customer data, schema/ledger state, available storage and connectivity; capture preflight output without secrets. Take and restore-test a staging backup/snapshot, choose maintenance window and stop on any identity mismatch. Execute once with scoped migration credentials and existing explicit confirmation only after approval, retain timestamp/exit/log and ledger evidence, and revoke credentials. On failure do not rerun blindly: stop traffic, inspect partial DDL/ledger, restore the verified snapshot or execute an owner-approved forward repair; recheck schema and readiness. This is a recovery plan, not a guarantee that the SQL is transactionally reversible.

## Phase 7A.1 provider compatibility decision — deployment blocked

**7A-01 remains blocked.** Render documents that its internal PostgreSQL endpoint has a self-signed certificate and does **not** support `verify-ca` or `verify-full`; its recommended internal `sslmode=require` would encrypt without the required CA/hostname authentication. The current application deliberately fails rather than downgrading. Render external PostgreSQL uses managed TLS, but an external path traverses the public internet; an exact CA/hostname verification and egress allowlist have not been demonstrated. The review-only blueprint now declares **no datastore resources**. Do not sync it or create a database pending a separately approved topology. Sources: https://render.com/docs/postgresql-creating-connecting and https://render.com/docs/blueprint-spec.

**7A-02 is configuration-mitigated, not deployed.** Render Key Value supports internal authentication, but defaults to unauthenticated internal URLs. The blueprint declares no Key Value resource, since a sync could otherwise create an unauthenticated instance. Under separate approval, create a dedicated instance, enable internal auth explicitly, disable external access and inject only its authenticated internal URL into both protected Redis settings; `STAGING_REDIS_HOST` must match its internal DNS name. Missing credentials, host mismatch, malformed URL and mismatched URLs now abort before constructing Redis clients. This URL check cannot prove server-side auth is enabled: an unauthenticated connection must fail in a later controlled provider test. No worker exists in this blueprint; a later worker requires separate credentials and ACL review. Never reference production Redis. Render's same-workspace, same-region services can reach private resources by default. Require a dedicated staging workspace (or independently verified Pro+ environment isolation), inventory every peer service and verify credentials, internal DNS, permissions and external `ipAllowList: []` in the authorized environment. Sources: https://render.com/docs/key-value and https://render.com/docs/private-network.

**7A-03 is partially resolved.** The health-only gate now requires a single exact `Host` matching `STAGING_ALLOWED_HOST`. Controlled tests cover missing/duplicate/wrong Host, parser-level conflicting/duplicate framing, chunked bodies, encoded paths, TRACE and forwarding headers; source checks verify that the configured server sets connection, request and header limits. The raw-HTTP fixture does not exercise Render's proxy and does not prove slow-client or connection-exhaustion resistance. Verify actual health probes, proxy rewriting, request limits, slow clients, private routing and quotas before any approval. The exact private service hostname/port and Redis hostname are owner-supplied configuration; values are unknown until a separately approved provider setup. An initial build with missing values must fail closed.
