## Threat model and trust boundaries

| Actor or input | Boundary and observed behavior | Remaining concern |
| --- | --- | --- |
| Unauthenticated external client | Reverse proxy → Express JSON parser → app-level `requireAuth` → verified-business dashboard limiter → route auth/ownership → staging gate → Multer. Multipart is not parsed by `express.json()`; missing/invalid JWT is rejected before Multer. | No deployed ingress body/concurrency policy was demonstrated. JWT verification precedes the business limiter, so that limiter is not a pre-auth abuse ceiling. |
| Authenticated malicious business owner | Upsert namespace is derived from the refreshed DB identity; form-supplied namespace is ignored. `.array('files', 3)` and `.single('file')` enforce expected file fields. | Up to three 50 MiB buffers per authorized upsert request; 120 requests/minute per business is not a simultaneous-request limit. |
| Cross-tenant attacker | JWT is checked against current business row; new HTTP upload jobs include business ID and namespace. Worker re-queries namespace and rejects a mismatched **present** business ID before reading/parsing the file; job polling checks namespace and present business ID. | Legacy queue records without `businessId` use namespace-only scope. A compromised BullMQ/Redis writer or shared filesystem is outside the HTTP authorization boundary. Worker trusts a path from its internal queue after that validation. |
| Crafted/aborted multipart client | Multer 2.5.0 has explicit file/field/part/field-name/value/index limits. Rejects malformed index and truncated boundaries; memory storage creates no disk file until the handler runs. | No measured peak RSS, abort latency under large concurrent streams, or proxy disconnect test. |
| File metadata attacker | `originalname` is reduced to a basename for the exclusive 0600 staged filename; worker uses original name/MIME for loader selection. | MIME/name are caller-supplied; malformed or oversized names may fail staging and be returned as queue-unavailable 503. Logs include the original name. File-content validation and log normalization are future hardening. |

Trust sequence: proxy trust is restricted by `TRUSTED_PROXY_CIDRS`; Express derives `req.ip`, verifies the JWT and DB business, then applies the per-business Redis quota. Upsert ownership precedes Multer. After Multer buffers an authorized file, the API writes it in `os.tmpdir()/chatflow-upload-staging` with exclusive creation and a job-ID name, records queued status in Redis, and submits the local path to BullMQ. The worker verifies namespace/business against PostgreSQL, reads the path, parses content, writes scoped chunks, and removes the source on success or final failure. Retries retain bytes; ambiguous queue acknowledgement retains bytes and a pollable ID rather than falsely claiming rejection. The cleanup scanner only removes aged app-managed files when the queue confirms absence. No distributed filesystem guarantee was found.

## Findings

| ID | Severity | Affected path and exploit prerequisites | Reproduction evidence | Mitigation and status |
| --- | --- | --- | --- | --- |
| B2-S1 | High for staging isolation | Original `blockStagingLegacyUploads` required both `CHATFLOW_ENVIRONMENT=isolated-staging` and the exact flag value `true`. A missing or malformed flag in an isolated staging API re-enabled authenticated legacy uploads. | Direct code inspection of commit `715dc81`; regression checks missing, `invalid`, `false`, and `true` flag values on both canonical/trailing-slash paths. | **Fixed in this assessment:** block whenever the isolated-staging marker **or** explicit disable flag is present. JSON text ingestion remains available. A deployment with both markers missing cannot be recognized as staging by the application; verify provider configuration and deny ingress paths before traffic. |
| B2-S2 | High deployment risk; exploitation requires a valid owner JWT | `POST /api/upsert` keeps up to three 50 MiB files in `memoryStorage`, at least 150 MiB of file payload per active request plus parser/Node overhead. Multiple simultaneous authorized requests can exhaust a small API container. | Limit constants and request-level 50 MiB + 1 rejection test; no concurrency semaphore or ingress body cap found. The 120/minute business limiter counts admissions, not simultaneous streams. | **Unresolved; file uploads stay disabled in staging.** Size an ingress maximum for multipart overhead and application request budget; derive an active-upload cap from measured container memory, baseline RSS, worker/process count and allowed concurrent requests. Add abort/latency/RSS tests through actual ingress before enabling. No safe numeric concurrency cap can be inferred from this repo. |
| B2-S3 | High deployment blocker for separate containers | API enqueues an `os.tmpdir()` path; separate Render web/worker services have no demonstrated shared volume. Valid queued jobs may fail to read source bytes. | `stageUpload`/`fileQueue.add`/`fs.readFile` code and staging blueprint define separate services; local fixture verifies only same-filesystem payload and cleanup. | **Unresolved.** Keep files blocked until a durable shared handoff is designed and verified end to end; no object-storage change in this batch. |
| B2-S4 | Low, authenticated input | File name and MIME are client-supplied and carried to logs and worker selection; overlong names can fail local staging and currently surface as 503. | `stageUpload` basename/exclusive open, upsert log, worker loader; no proof of cross-tenant read or arbitrary path write through HTTP. | Validate/normalize metadata and distinguish input errors from queue outages in a later scoped change; do not claim the declared MIME proves content type. |

No unauthenticated Multer parse or unauthorized queue submission was reproduced with the controlled fixtures. These are negative test results, not a guarantee against every malformed stream or a deployed ingress bypass.

## Security control verification

- **Authentication/authorization:** code inspection shows app-level JWT DB revalidation and business quota precede both Multer handlers. The app-level quota is separately tested with stub routes; real-router multipart fixtures test route auth/ownership. Upsert's `requireKnowledgeOwner` precedes parsing. Scrape file repeats `requireAuth` on the same verified request. Missing/invalid JWT, inactive account, missing bot, widget token, and foreign business payloads are rejected or scoped to the verified tenant in route tests.
- **Routes/aliases:** only `app.use('/api/upsert', upsertRoutes)` and `app.use('/api/scrape', scrapeRoutes)` register the legacy handlers. Trailing slashes match the same POST route; PUT has no upload handler. No application-level alternate alias was found. Proxy rewrites were not tested; inspect the deployed router/ingress rules before traffic.
- **Multipart:** upsert allows three 50 MiB files, one 100 KiB text field, four valid parts (Busboy sentinel `parts:5`), 32-byte field names, `fieldArrayIndexLimit:0`; supplemental file allows one 5 MiB file, zero fields, one valid part (sentinel `parts:2`). Unexpected file fields, excess parts/fields, duplicate/conflicting text fields, giant numeric index, oversized files, empty forms and malformed boundaries are rejected in controlled requests. Error handler maps Multer violations to 400 or 413 and recognized malformed boundaries to 400. Unexpected parser errors still reach the global handler.
- **Abort/cleanup:** aborted request fixture leaves no job and the server answers the next request. Rejected in-memory uploads do not reach `stageUpload`. Accepted file sources use exclusive private files; rejected enqueue cleans sources when rejection is known; retries/final failures and age/queue-aware orphan cleanup are covered by existing tests. No live crash/RSS characterization under adversarial concurrency was performed.
- **Staging:** `CHATFLOW_ENVIRONMENT=isolated-staging` now blocks file ingress regardless of missing/invalid upload flag, while `STAGING_DISABLE_LEGACY_FILE_UPLOADS=true` also blocks if the environment marker was omitted. The example and blueprint set both, but the blueprint still pins `fix/tenant-security-boundaries`, not this PR's code. Text-only `/api/upsert` JSON and `/api/v1` knowledge flow remain available. Confirm the deployed commit, configuration and proxy routing on the actual service before claiming any staging protection.

## Dependency and deployment decision

The lockfile retains `multer@2.5.0`, `proxy-addr@2.0.8`, `protobufjs@7.6.6`, `@grpc/grpc-js@1.14.6`. Upstream GHSA-535w-7cp7-47q4 affects Multer `<2.3.0`; newer aborted-upload advisories affecting 2.3/2.4 are patched by 2.5.0. The original array-index advisory was absent from npm audit, so the upstream patched range and crafted-field test are separate evidence.

Keep staging file uploads and website agents disabled. Do not merge or deploy Batch 2 until the assessment patch has passed CI, independent assessment review has been recorded, and the owner approves the normal release process. Even after code review, maintain the file-upload deployment blocker until deployed ingress memory policy and cross-container handoff are proven. Do not run migrations for this assessment.
