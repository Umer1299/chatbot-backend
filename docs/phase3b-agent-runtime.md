# Phase 3B — isolated website agent runtime

Phase 3A's management agents remain channel-independent. Migration 011 adds distinct runtime tables for website deployments, text knowledge and vectors, sessions/messages, leads and inquiries. It adds `agents.knowledge_revision`. It does **not** add an agent UUID to legacy tables or reinterpret legacy `messages.agent_id` text. Existing bot IDs, legacy sessions, sources, leads, inquiries, domain settings, RAG cache and `/api/chat` stay untouched. Old businesses' mapped draft agents receive no copied runtime records. New agents start with empty knowledge and history.

Migration 012 adds short-lived, ownership-scoped website-chat turn claims keyed by the globally unique session ID. A concurrent turn returns 409 before embedding or model work and may be retried after the active turn completes. Claims are removed in `finally`; a 15-minute expiry permits recovery after process termination without reserving a PostgreSQL pool client during external provider calls. Apply both 011 and 012 before enabling the runtime.

## Ownership and persistence

All new resources have business UUID and agent UUID, with composite FKs to their parent. Sessions additionally reference the exact deployment, and messages/leads/inquiries carry composite FKs to that session. `agent_chat_sessions.id` is globally unique within this new runtime; a collision with another agent or deployment cannot reassign an existing session. Legacy sessions live in a separate table. Distinct source and chunk tables prevent both accidental legacy access and partial agent filtering in old ingestion/RAG routes. Legacy file jobs continue to write only to legacy knowledge.

`agent_knowledge_sources` owns unique `(agent_id,source_key)` text sources. Source replacement embeds the entire new text first, then locks the agent and changes its chunks in one transaction. A retry with identical content is a skip, with an exact inserted/skipped result. There is no partial commit for a text replacement; failures leave prior content intact. Database statement triggers increment **only that agent's** durable revision in the same transaction as chunk insertion/deletion/update. The new `rag:agent:v1:<business UUID>:<agent UUID>:<revision>:<SHA-256(query,limit,threshold)>` cache is disjoint from old business cache keys. Retrieval checks the revision before using cached data and after querying PostgreSQL; Redis errors fall back to the database, while missing/failed database revision checks fail closed. No Redis key scans. Only the new source/chunk tables are searched; no implicit sharing.

Deployment identity is a business+agent-scoped website record with distinct public UUID, explicit HTTPS origin list (loopback HTTP permitted for development), paused/active status and versioned SHA-256 verifier of a uniformly random 256-bit bearer token. Creation and rotation reveal plaintext only once. Public IDs do not authorize chat. Rotation replaces the verifier and increments its version; revocation replaces the verifier and pauses the deployment without disclosing a replacement token. The application verifies token, current business/agent/config/model status and exact origin before chat writes. Origin is a secondary policy, never a credential. Public cookies are not used.

`AGENT_WEBSITE_ENABLED=true` is required explicitly for public `/api/agent-chat`; absent/false is fail-closed 503. Apply 011 and verify credentials/policies before enabling in staging. Existing public traffic is never routed to it automatically. The independent `agent-chat-ip` Redis quota (300/min per IPv6-safe IP) bounds unauthenticated lookup work; Redis quota failure blocks the request. Browser preflight accepts a valid origin without credentials for this **new route only**; the actual request must pass PostgreSQL's deployment allowlist. Legacy widget CORS rules and exact credentialed dashboard origins remain unchanged.

The new chat response uses `reply`, `creditsUsed`, `usage` and a familiar SSE `ready`/text/`meta`/`[DONE]` shape. The first implementation buffers a unary model completion and emits it as one SSE text event; incremental provider token streaming is a later enhancement. A paused agent with a valid active deployment returns a disabled reply with zero credits and no writes. Invalid/revoked/paused deployments, invalid origins, disabled businesses, unsupported models and unconfigured/draft/archived agents are denied before writes. Model/embedding failures do not commit sessions or outcomes. SQL writes of session, paired messages and matched lead/inquiry happen in one transaction. The deterministic lead detector is reused for explicit contact capture; support/return/refund/problem/issue/complaint messages create scoped inquiries. Neither new resource is exposed by legacy lead/inquiry endpoints. This rule-based classification is pilot behavior; richer, audited extraction and usage metering are follow-up work. Provider/model selection is verified against the active model catalog. The new completion adapter uses the existing provider SDKs and server-managed API keys; no key comes from agent configuration.

Admission is checked again under database row locks after model generation. A credential rotation, deployment revocation, agent pause or model deactivation during generation cannot commit the in-flight conversation after that change.
The initial `agent_configs.version` is part of that admission snapshot. The locked recheck requires the same version before any session, message, lead or inquiry write, so prompt, tool, lead-field, escalation or generation-setting edits reject the in-flight response with a retryable conflict. No SSE success event is emitted until the transaction commits.
Agent configuration, activation, deployment activation and both admission checks enforce the business plan against the catalog model's `min_plan`; a downgrade prevents use of a previously configured higher-tier model without mutating that configuration. Provider token counts drive the same estimated-cost credit formula and model prices used by legacy chat; missing provider counts use a text estimate. This response usage is informational until durable usage/billing events are added in a later phase. The legacy `modelService.getSafeModel` entitlement behavior is separate and should be reviewed before relying on plan limits for existing bots.

## API contracts and Next.js integration
Management mutations use the post-lock business authorization snapshot for model entitlements. A concurrent plan downgrade cannot approve a premium model based on an earlier read.

For all `/api/v1` routes, use the Phase 2 Better Auth **cookie** and trusted dashboard `Origin`, with JSON mutation bodies. The backend checks current agency/business membership, and only owners/admins or explicitly granted business editors may manage knowledge, deployments and sensitive conversations/leads/inquiries. A business viewer gets metadata from Phase 3A but cannot read these sensitive resources. Legacy JWT and public deployment tokens are never accepted here. The server derives business/agent/deployment from checked ownership; caller IDs alone are never authority. Next.js should call through a server-side BFF/proxy forwarding the secure session cookie with appropriate CSRF origin handling, and keep one-time deployment tokens out of logs, public server-rendered pages and management state. Store the public token only in the intended website embed configuration; restrict its allowed origins and rotate it if exposed. A token grants chat only.

- Configure an agent: `POST /api/v1/businesses/{businessId}/agents` `{ "name":"Sales", "purpose":"lead_generation" }`; `PUT /api/v1/businesses/{businessId}/agents/{agentId}/config` with full validated configuration and `expected_version`; `PATCH .../{agentId}` `{ "status":"active" }` after config is active.
- Add/replace text knowledge: `POST .../{agentId}/knowledge` `{ "source_key":"pricing", "text":"Our packages..." }`. The same key replaces this agent's source atomically. `GET .../{agentId}/knowledge` lists source metadata; `DELETE .../{agentId}/knowledge/{knowledgeId}` removes one source.
- Create a paused website deployment and issue its token once: `POST .../{agentId}/deployments` `{ "allowed_origins":["https://client.example"] }`. Inspect metadata with `GET .../{agentId}/deployments`; activate with `PATCH .../{agentId}/deployments/{deploymentId}` `{ "status":"active" }` after the agent is ready. `POST .../{deploymentId}/rotate` returns a new token; `POST .../{deploymentId}/revoke` pauses and revokes with no token returned. A PATCH also accepts a replacement `allowed_origins` array. Never expect GET to return the verifier or original secret.
- Website chat: `POST /api/agent-chat` with `Origin: https://client.example`, `x-agent-token: wct_<secret>` and `{ "sessionId":"opaque-unique-visitor-session", "message":"What does pricing include?" }`. Add `?stream=true` for SSE. The browser must use a fresh unpredictable session ID per conversation, retaining it for subsequent messages; the public token is rotated independently of agent identity.
- Dashboard reads: `GET .../{agentId}/conversations`, `GET .../{agentId}/conversations/{sessionId}`, `GET .../{agentId}/leads` and `GET .../{agentId}/inquiries`. Lists are capped at 100 records; pagination and richer workflow actions belong in later work.

## Staging and rollback

Migration 012 must follow 011. It creates only `agent_chat_turn_claims` and its expiry index; replay is idempotent and no historical resource is modified. The reviewed staging sequence is now 005→006→007→008→009→010→011→012.

Migration 013 follows 012 and adds an equivalent expiring business claim for legacy knowledge replacement, supplemental ingestion and deletion. Embedding calls and batch delays hold no pool client; each write transaction fences on the exact claim token. Concurrent mutations return a retryable conflict. The reviewed staging sequence is now 005→006→007→008→009→010→011→012→013.

Apply reviewed migrations 005→006→007→008→009→010→011→**012** against an isolated staging backup, with the runtime flag still off. Migration 011 uses the existing ledger/advisory lock, creates separate tables and adds an agent revision column, then installs per-agent revision triggers. Migration 012 creates only the expiring turn-claim table and index. Reapplying either migration does not duplicate rows or reset revisions. Verify exact before/after legacy businesses/bots/configs/history/leads/inquiries/knowledge/settings, counts and samples; verify FK constraints, DDL lock duration, model availability and pgvector index creation. Run the two-agent CI scenario again against staging with mocked/approved model calls before enabling the flag; test actual credential delivery, allowed domain, Redis fail-closed behavior, concurrency and token rotation. Do **not** run production migrations in this PR.

Rollback the application and disable the flag first. Leave new tables intact to preserve created agents, deployments, conversations and knowledge. A schema rollback would require an exported inventory and separate approved data migration; do not drop or reset customer data. There is no implicit historical backfill. A future opt-in migration may map verified historical resources from a business to its explicit `legacy_agent_mappings` row after reconciling exact counts and ownership, with reversible batches; never infer agent IDs from old message labels or contents.

The previously documented production prerequisites remain: staged migrations and backup/restore, supported Node runtime and trusted proxy/HTTPS/session configuration, durable policy and Redis tests, and proven API-to-worker temporary upload handoff if API/worker are separate containers. The old upload topology remains a blocker; new text knowledge bypasses files and BullMQ. No WhatsApp, voice, Calendar, n8n, object storage, payment, frontend or dashboard is implemented here.

Legacy supplemental uploads, website replacement and deletion now share a PostgreSQL per-business advisory lock for the full mutation. A deletion cannot report success while an already-running multi-chunk upload later restores knowledge; partial supplemental commits and retry reporting remain intact. Name-only agent lead capture requires an explicit introduction such as “My name is Alex Customer,” stores that selected field immediately, and preserves it when intent appears on a later turn; routine phrases are not stored as names. Removing an agency membership deletes only agency-staff grants, preserving a separately issued client-business grant.
